# AGENTS.md - Project Rules & Development Guidelines

This document defines the core principles, design standards, and mandatory technical rules for all AI Agents and developers contributing to this codebase.

1. **Design & UX Philosophy**: Minimalist, monochromatic, zero-emoji in user-facing UI and backend logs. Web UI supports bilingual i18n (`vi` default with full diacritics, `en` secondary). Codebase, documentation, commit messages, and tooling must be 100% English. The single sanctioned exception is `README.vi.md`, a Vietnamese quickstart for end users: a deliberately partial document covering prerequisites, launch commands and service ports — not a translation of `README.md`. The canonical documentation is `README.md`, and everything under `docs/`, including sprint guides and reports, is English-only.

2. **Sound Solutions & Root-Cause Verification (Never Fear Effort)**: When implementing any issue or task, never shy away from implementation effort or labor. Never choose sloppy, convenient shortcuts, superficial band-aids, or quick hacks out of convenience or fear of complexity. Always investigate and resolve problems at their absolute root cause, architect the soundest, most maintainable solution for the system, and verify exhaustively end-to-end before considering any task complete.

3. **Issue Estimation Mandate**: Before starting any issue or task, AI agents and developers MUST provide an explicit completion time estimate (active effort hours/days and expected delivery window) based on task scope. The estimate must honestly reflect the full effort required for sound, root-cause implementation per Rule 2, never anchoring to premature shortcuts.

4. **End-to-End Bug Reproduction**: When investigating any bug or regression, you MUST simulate and reproduce the failure end-to-end from a real user/client perspective before attempting fixes. Passing unit tests alone is NEVER sufficient.

5. **Git Flow & Zero Direct Push**: Direct push to `main` and `dev` is strictly prohibited. Create feature/fix/doc branches (`feat/*`, `fix/*`, `docs/*`), push, and open PR targeting `dev`. AI agents must NEVER auto-merge PRs.

6. **Living Documentation & Holistic Knowledge Maintenance**: Whenever any task or PR is implemented or merged, developers and AI agents MUST holistically audit and synchronize all related documentation across the repository:
   - Update any relevant topic, architecture, operational, sprint, or guideline files under `docs/` directly affected by the changes (e.g. execution guides, ADR references, data schemas, API catalogs).
   - Record a new engineering lesson as a new `docs/lessons/L<NN>-<slug>.md` plus one row in `docs/lessons/INDEX.md`. Never append to a single register file — that is how the 143 KB monolith was created.
   - Update root `README.md` (English, canonical) whenever public features, developer workflows, instructions, setup commands, or system architectures are affected or expanded. If the change alters prerequisites, `make` targets, service ports or endpoints, mirror it in the `README.vi.md` quickstart in the same commit: that is the only part of the Vietnamese file kept in sync, and `tools/docs/check_readme_vi_parity.py` enforces it. A full translation of `README.md` is explicitly not maintained — do not recreate one.
   - Codebase, git history, and PR list remain the sole source of truth; never fabricate claims.

7. **Architecture Standards**: Follow leaf modulith pattern in `services/go-server` (see `GO_BACKEND_ARCHITECTURE.md`). Hand-written SQL only (no ORM). Never fetch snapshots directly from frontend; use backend proxy cache. Run `make swagger` on API route changes.

8. **Zero Hardcoded Secrets & Mandatory Environment Configuration**: Hardcoding API keys, access secrets, private tokens, passwords, or credentials in any form (including offline test scripts, evaluation tools, benchmark harnesses, utility CLIs, or documentation files) is strictly forbidden. All secrets must be dynamically loaded from `.env` (which must remain strictly gitignored) or environment variables. When writing environment fallback functions or parameter defaults (e.g., `os.getenv("KEY", "")`, `config.Get("KEY", "")`), the fallback value MUST strictly be `""` (empty string) or trigger an immediate fail-fast termination (`os.Exit(1)` / panic / fatal log). Never place real, mock, or placeholder credential strings as fallback arguments in executable code. Example configuration templates in `docs/` and `.env.example` must use uppercase angle-bracket placeholders only (e.g., `R2_ACCESS_KEY_ID=<your-access-key-id>`).

9. **PR Issue Linking Format Mandate**: When creating a Pull Request that addresses or implements an issue or sprint task, the PR description MUST strictly start with `Close #<issue-number>` (e.g. `Close #297`). AI agents and developers must NEVER use informal, non-linking phrasing such as `Addresses Issue #209`, `Addresses #209`, or `Implement #209` because GitHub's issue closing automation exclusively parses standard closing keywords (`Close #<number>`) to link PRs and auto-close issues upon merge. Sprint and task progress is tracked on the org GitHub Projects v2 board **ProjectKV** (https://github.com/orgs/529-studio/projects/2); the legacy 529 Studio Hub (Plane) Kanban card format `closes [KV-<card-id>]` is RETIRED since the Hub was decommissioned (10/2026, per ADR-011 D6) and MUST NOT be used in new PRs. All PRs must adhere to `.github/pull_request_template.md`.

10. **Proactive Manual Testing Scenarios & End-to-End Self-Verification**: Before pushing commits to a remote branch, opening a Pull Request, or considering any issue or task resolved, AI agents and developers MUST proactively design an explicit, practical manual testing scenario checklist (simulating real-world user interactions on the UI, browser workflows, CLI commands, and backend API endpoints). The agent MUST autonomously execute and self-test each scenario end-to-end on live running services (capturing empirical evidence, visual UI screenshots, API payloads, and console telemetry) and report the results clearly to the human collaborator. Passing automated unit tests alone is NEVER sufficient; an issue is only considered ready for closure and PR creation once all manual test scenarios pass with verifiable empirical proof.

11. **Context Budget & Partial Reading**: Documentation is read on every task, so its size is a cost paid repeatedly rather than once. A document is never loaded without first locating the part you need.
    - **Always-loaded set** — `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `docs/ONBOARDING.md`, `docs/lessons/INDEX.md` — must total **36 KB (36,864 B) or less**, and no file in it over **16 KB (16,384 B)** — except `docs/lessons/INDEX.md`, which gets **20 KB (20,480 B)** because it is a table of one row per lesson and the tighter cap made every new lesson erode an existing guardrail (L66). These load on every task, so a byte here costs roughly an order of magnitude more than a byte in a report. A change that would exceed either limit moves detail into an on-demand document and leaves a link.
    - **On-demand files** — `README.md`, every ADR, report, runbook and sprint guide — ceiling **25 KB (25,600 B) each**, and they are read in ranges, never wholesale: locate with `grep -n`, then read `sed -n '<start>,<end>p'` or the read tool's offset/limit. State why if a full read is genuinely required. A file already over its ceiling is an exception recorded in the docs-lint configuration: it may not grow, and the list only shrinks.
    - A document over 25 KB ships a navigation aid in its first 40 lines — a table of contents, or a companion INDEX with one row per section. `docs/lessons/INDEX.md` is the model. A document over 100 KB is a defect: split it, or record a dated exception under `docs/reports/`.
    - Never duplicate content across the two tiers. The entry file states the rule, the on-demand file holds the detail, the entry file links to it. Duplication is how the 143 KB lesson register and the 41 KB bilingual README were built.
    - `make docs-lint` enforces these numbers once it lands; until then review does.
